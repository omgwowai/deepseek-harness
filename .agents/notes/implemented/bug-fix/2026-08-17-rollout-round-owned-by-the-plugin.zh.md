# Agent Note: rollout 轮次归插件所有，而非归开启它的触发方

Status: implemented

[English](2026-08-17-rollout-round-owned-by-the-plugin.md) | 中文

## Problem

`tokenrouter-rollout` 会派生 N 个 worker 子代理并行地为同一个决策做规划，由一个 SOTA judge 为它们的方案打分，再把胜出者交回给代理。对这个尚未发布的扩展做的一次排查发现：它开启的任何一轮都无法抵达那个结果，而其中若干失败并不体现在会话日志里，因此不只是"坏掉"那么简单。

起支配作用的缺陷是：`runRound` 从"谁请求了这一轮"那里取得取消信号。`/rollout` 命令处理器在 worker 派生完毕后即刻返回，而 UI 请求的 `AbortSignal` 会在该响应关闭时中止，于是这一轮的 worker 在启动的同一个 tick 里就被中止了。每一轮都以 `all workers failed; nothing to judge` 收场——直接观察到的现象是两个 worker 的信号均为 `aborted: true`、两条轨迹的文本均为 `cancelled`、两次已启动的运行对应 `dispose` 调用为零。即便某一轮熬过了取消，它也不会被读到：胜出方案是用 `agent.inject()` 交付的，该方法只向收件箱追加而不会唤醒空闲的 driver，而一轮要花上几分钟——等到方案存在时 driver 通常已经空闲，插件里没有任何东西会唤醒它。

在这两点之后，排查还发现了一类"产出错误结果"而非"没有结果"的轮次。超时或出错的 worker 会把失败详情放在与方案相同的 `text` 字段里返回；judge 会把这些字符串和真正的方案一起打分，于是 `worker 2 ended with error: …` 有可能赢下一轮，并作为"当前采纳的决策"交付给代理。`outputTokens` 在 `TrajectoryOutcome`、`rollout/trajectory` 事件以及统计折叠三处都有声明，却从未被任何代码填充，因此面板上的 `workerOutputTokens` 恒为 `0`——一个因缺失而不存在的测量值，被当作"测得为零"展示。`DiversitySlot` 带有一个 `temperature` 字段，而 `AgentOptions` 并没有承载它的位置，于是每个 slot 的 temperature 都被丢弃、N 条轨迹完全同质，这恰恰抹掉了该插件存在的意义——多样性。

另有两个缺陷在用户的实际配置下即可触及。`session/event` 是全局事件流，因此 rollout worker 自己的 `todo/write` 会抵达里程碑监听器；由它派生的一轮，其 worker 又会派生更多轮次——由一个已完成的里程碑引发的无界递归，而 `autoMilestone` 只差一个开关。此外，judge 端点是硬编码的主机：某个运维方的内部网关 URL 同时出现在配置 schema 的默认值、`DEFAULTS` 与 `cordis.patch.yml` 中，于是每一处安装都会把自己的 judge 流量指向一台并不属于它的主机。

## Decision

一轮是插件的一次操作，其生命周期、取消与交付方式据此确定，而不取决于触发方。

取消由插件自有的 `AbortController`（`this.rounds`）承担，随控制器创建，仅在销毁时中止。两个触发路径都传入 `roundSignal`；除此之外没有任何东西能取消一轮——这正是"让一轮活过请求它的那次请求"所付出的代价。交付使用 `agent.steer()` 而非 `agent.inject()`：steer 会在空闲 driver 上开启一个轮次，在运行中的 driver 上则于最近的步骤边界被消费，这覆盖了手动触发（用户在等待、driver 空闲）与里程碑触发（driver 处于轮次中）两种情形。

judge 只为 `ok` 轨迹打分。`candidates` 把 judge 那套密集的 `0..n-1` 编号映射回轮内索引，使 `rollout/selected` 与轨迹日志在候选集被过滤后仍然对齐；当没有候选存活时，该轮报告 `all workers failed; nothing to judge`，而不是选中一条失败字符串。`outputTokens` 由子会话 assistant 消息的 usage 求和得到；当子代理是远程运行、或适配器根本不报告用量时，它保持**缺失**而非零，这样统计折叠就不会把一个缺失的测量读成一条免费轨迹。

judge 端点归部署方与用户所有，绝不归插件所有。`judgeBaseURL` 没有默认值；启用却未设置该值的插件在加载时抛错，而由于设置分区可以在加载之后启用 rollout，`runRound` 会在派生 worker 之前再次抛错——在那里拒绝不会让这一轮损失什么，而先派生则会白白烧掉 N 次 worker 运行，其方案无人可评。设置页承载了该字段，清空时执行 unset 而非写入 `''`，因此清除用户覆盖值会重新继承部署方的值，而不是用一个空字符串把它盖住。

多样性是提示词层面的，并且明确如此声明。`temperature` 已从 `DiversitySlot` 中移除；一个 slot 改变的是"要求 worker 做什么"（`strategy`），而不是"采样器如何行为"，逐轨迹的采样差异被记为待办工作，它需要在每个子代理上接入 `agent/request` waterfall。

## 排查中发现的、轮次归属之外的缺陷

里程碑监听器会跳过任何持久化 header 中记录了 `origin: 'subagent'` 的会话。该 header 是权威事实——它在子代理创建时写入并能在重载后存活——而由控制器持有的"已派生子代理登记表"并不具备这一性质。它的 `next === undefined` 分支（一次写入完成了某个里程碑、却没有留下待办的下一项）此前没有测试；现在有了一个经变异验证的测试，README 也把"此时不触发"记为有意为之，而非一处缺口。

`workerSubagentProvider` 取代了硬编码的 `'fork'`。默认值仍是 `fork`——它让每个 worker 带着父代理已完成轮次的历史起步——但这条路由现在和其他所有随部署而变的选择一样，是一个受校验的配置字段。

还有三个缺陷位于 composer 按钮里，是逐文件覆盖率闸门把它们暴露出来的。`aliveRef` 缺少配对的 `useEffect` 来清除它，于是两条 settle 路径上的"卸载后守卫"形同虚设。一处 `if (!enabled || running) return` 守卫重复了设置 `disabled` 的同一条件，因而永远不会执行——按仓库中"不可达守卫"的惯例将其删除并留下注释。以及 `css.wrap` 在 CSS module 中并不存在，于是 `?? ''` 兜底在每次渲染时都会触发，按钮与其错误行根本没有 flex 包裹容器；该类名现已存在，兜底也随之移除。

## Alternatives considered

**保留触发方的信号并让请求挂起。** 让 `/rollout` 等待整轮结束，从而使其信号保持有效。之所以否决：这与该功能本身相悖——一轮要花几分钟，而一个会阻塞几分钟的命令根本无法从 composer 发出；里程碑触发更是从一开始就没有可供挂起的请求。

**用 `inject` 交付并附加一次显式唤醒。** 保留收件箱语义，由插件在追加之后推一下 driver。之所以否决：这让一次交付有了两个所有者——唤醒方必须知道 driver 的状态才能避免打断正在进行的轮次，而这恰恰是 `steer` 已经持有的状态。在插件里再开一条唤醒路径，就是与循环自身维护的那条竞争。

**让 judge 自己识别失败文本。** 把全部轨迹都传过去，并要求 judge 给明显失败的项打零分。之所以否决：这会为调用前就已确知不是方案的字符串花费 judge tokens；而且它让正确性依赖于 judge 是否照做——一个把看似合理的错误信息排在首位的 judge 会把它作为决策交付出去，而这正是要防止的失败。

**内置一个默认 judge 端点。** 把该扩展开发时所用的网关设为 `judgeBaseURL` 的默认值。之所以否决，理由有两条且彼此独立：端点是部署方的属性而非本插件的属性；而那个具体取值是某个运维方的内部主机，不应被分发给既无法访问、也不应被告知它的安装环境。

**登记已派生的子代理，而不是读取 header。** 让控制器记录自己派生过的会话 id，并据此过滤事件流。之所以否决：该集合是进程内的，重载即清空，而递归风险并不会随之消失；何况子代理在其结果 settle 后即被销毁——监听器要查询的集合，届时已不再包含它正在判断其事件的那个会话。

**为 temperature 接入逐子代理的 `agent/request` waterfall。** 保留该字段，让采样多样性成为现实。之所以否决：这是对子请求路径的改动而非对本插件的改动，超出了一次缺陷修复的范围；提示词层面的多样性才是真正落地的机制，因此那个"承诺多于交付"的字段被移除，而不是继续接受它会丢弃的取值。

## Testing

`packages/extensions/tokenrouter-rollout` 有 22 个测试，逐文件覆盖率 100%。里程碑监听器是在组合后的控制器上被检验的——真实代理追加真实的 `todo/write` 事件，由插件自己的监听器做出判断——观测点设在 `ctx.subagents.start`，即被触发的一轮最先做的事；递归守卫与"无待办下一项"守卫在那里经过了变异验证。`runRollout` 覆盖了过滤后的候选集（胜出者以轮内索引报告）、逐轨迹的子代理输出 token，以及全部 worker 失败的路径。

`packages/client/ui-rollout` 有 23 个测试，逐文件覆盖率 100%，其中包含此前完全不存在的三个 React 界面的渲染测试。按钮的失败呈现覆盖了"返回失败行""`Error` 拒绝""原始字符串拒绝"三种情况，两条 settle 路径也都在卸载之后被检验。设置页覆盖了 `judgeBaseURL` 与 worker 池在清空时的 unset 行为；apply 层的镜像覆盖了 inject 时的采纳、后续写入抵达两个 store 句柄、inject 之前发生的写入，以及尚在加载中的 scope。

## Consequences

轮次现在能够跑完，其胜出者也能抵达代理——这正是让该扩展可用的前提。统计面板报告的是真实的 worker token 消耗，一轮也不再可能把某个 worker 的错误信息当作方案交付。

代价是有意为之的，并记入了 README 的限制小节：由于取消权归插件所有，单独取消某一轮是做不到的——只有卸载插件才能中止它，而进程退出时仍在飞行中的轮次会丢失。使用 steer 也意味着里程碑触发的方案可能落在用户并未主动请求的某个步骤边界上，而这与"它能够抵达"是同一个性质。

移除端点默认值，把一个必需的决定交给了启用 rollout 的人；那两处抛错让这个决定在加载时、以及在任何 worker 花费 token 之前，各响亮地失败一次。因此在启用状态下，`judgeBaseURL` 是部署方唯一不能省略的字段——该包的 README 对此有直接说明。
